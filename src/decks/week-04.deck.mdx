## Define the budget's unit

Lab limit: **150 Unicode code points in the original text**, including spaces and punctuation.

JavaScript `text.length` counts UTF-16 code units; `[...text].length` counts code points.

We do not trim or normalise before counting. Visible characters can contain several code points.

[MDN: string length and iteration](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/length)

## Test the boundary · 6 min

Count **150 ASCII letters**, then append one space.

In JavaScript, compare the length of `"\u{1F600}"` with its code-point count.

Compare `"\u00E9"` with `"e\u0301"` under our no-normalisation rule.

Does an empty string pass the budget? Does that make it a useful bio?

---

## Budget answers

150 letters pass; an added space gives **151**, so reject the budget check.

U+1F600 occupies **two UTF-16 units, one code point**.

The two accented forms count as **one and two code points** here.

Empty text passes the length ceiling but provides no clarity evidence.

---

## Declare the tokenizer

Lowercase; take maximal runs of **ASCII a–z and 0–9**.

Spaces, punctuation, apostrophes and hyphens separate tokens.

Keep all words and numbers. No stemming or stop-word removal.

This deliberately narrow English exercise needs a different tokenizer for broader language coverage.

## Trace the matcher · 6 min

Dictionary: **“must love dogs”** and **“partner in crime.”**

Tokenise “Must love dogs; partner-in-crime.” Count the matched share.

Then match “partner in crime” against both **“partner in crime”** and **“in crime.”**

Count each covered token once, even when phrase spans overlap.

---

## Matching answers

First input: **six tokens, six covered → 100%**.

Overlapping phrases: **three distinct covered tokens / three → 100%**, not 5/3.

Full bio A: **3/14 ≈ 21.4%**. Full bio B: **0/20 = 0%**.

No tokens means an undefined share. Report it explicitly; do not call it 0% repetition.

## The hidden weights are arithmetic

<div className="deck-formula">A: 0.8 × 30% + 0.2 × 10% = 26%</div>

<div className="deck-formula">B: 0.2 × 35% + 0.8 × 15% = 19%</div>

The weighted averages describe different mixtures.

This constructed reversal is often called Simpson's paradox.

## Design the comparison you wanted

Hold the photo and case facts fixed. Freeze both candidate texts before allocation.

Assign variants **randomly within each zone**, retaining one assignment per simulated viewer.

Record the zone in the analysis, not just in the raw file.

[NIST: randomized block designs](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)

## Define one primary outcome

Example protocol: **a binary positive response within 24 simulated hours of first exposure**.

Denominator: every assigned simulated viewer, counted once.

A complete window with no positive is 0. Missing observation is not automatically 0.

Missing records or duplicate assignments fail this classroom run's data check; repair before analysing.

---

## Freeze the stopping rule too

Stop allocation at **500 viewers per variant per zone**. Then complete every observation window.

Primary estimate: mean of the two zone differences, with **50/50 weights**.

Declare **+3 percentage points** as an illustrative minimum worthwhile effect.

The 2,000-viewer cap is a teaching choice, with no power guarantee. The protocol has no outcomes yet.

## A separate balanced fixture

<DeckBars caption="Invented independent-binomial arithmetic fixture · unrelated to the CSV totals" maximum={100} scale="Bar scale: 0–100% positive responses. These are not outcomes of our proposed trial." rows={[
  { label: 'A', value: 12, display: '120 / 1,000 = 12%' },
  { label: 'B', value: 14, display: '140 / 1,000 = 14%' }
]} />

Observed difference: **+2 percentage points**.

---

## Points and percent are different units

Absolute change: **14% − 12% = 2 percentage points**.

Relative change: **(0.14 − 0.12) / 0.12 ≈ 16.7%**.

“B is 16.7 points better” is an arithmetic error.

Neither expression tells you whether the difference is distinguishable from sampling variation.

---

## Build the equal-rate null model

Assume independent binary observations with a stable probability in each arm.

Under **H₀: pA = pB**, estimate their shared rate:

<div className="deck-formula">p̂ = (120 + 140) / 2,000 = 0.13</div>

[NIST's two-proportion method](https://itl.nist.gov/div898/handbook/prc/section3/prc33.htm) gives the pooled standard error for this test.

---

## Scale the difference by its uncertainty

<div className="deck-formula">SE₀ = √[0.13 × 0.87 × (1/1000 + 1/1000)]</div>

<div className="deck-formula">SE₀ ≈ 0.01504; z = 0.02 / 0.01504 ≈ 1.33</div>

A two-sided 5% normal test compares **|z| with about 1.96**.

Our sign convention is always B minus A.

---

## Audit the calculation · 6 min

Reproduce 120/1000 versus 140/1000 in the [calculator](/toolkit/#experiment) or workbook.

Explain the **0.13**, **0.01504** and **1.33**, with their units.

Reverse the arms. Which values should change sign?

Write a result sentence that does not announce equivalence or a causal winner.

---

## What the result permits

**1.33 < 1.96:** no clear difference under this model and threshold.

Swapping the arms changes the signs of the difference and z; the pooled rate and SE stay fixed.

Non-rejection does not establish equivalence.

The +2-point estimate is below our example +3-point worthwhile effect, but that comparison alone does not rule out worthwhile effects.

## Sparse counts need a different route

Try **2/8 versus 4/8**. The course calculator withholds its normal approximation.

Its guard requires at least **10 in every positive/negative cell**; this is a conservative course choice.

It implements no exact test, power calculation or equivalence test.

Increasing synthetic counts does not create real-world evidence.
